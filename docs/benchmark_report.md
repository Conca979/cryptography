# Experimental Benchmarking Report: Tile-Level Transposition vs. Chaotic Pixel Permutation

## 1. Experimental Methodology and System Setup

### 1.1 Objective
This empirical study evaluates the computational latency, memory footprint, and compression storage penalty of Tile-Level Transposition ciphers proposed by Lan and Wang (IEEE Access 2025). The goal is to evaluate their viability for anti-scraping image protection systems operating over real-time HTTP delivery networks and HTML5 Canvas client viewports.

The benchmark:
- **Baseline Plaintext**: Unencrypted source image.
- **Generalized Rectangular Transform**: 4-condition modular affine tile permutation with origin-displacement translation vector $(r_m, r_n)$.
- **Client-Side JavaScript IGRT**: Production client-side HTML5 Canvas decoder (`igrt_client.js`) evaluated via Node.js V8 execution of `descrambleBuffer32IGRT`.

### 1.2 Hardware and Environment Configuration
- **Interpreter**: Python 3.10.0 (MSC v.1929 64-bit) / Node.js v22.19.0 (V8 12.9)
- **Dependencies**: Strictly Pillow (PIL), NumPy, and standard library modules (no third-party native C extensions or network calls)
- **Statistical Protocol**: $K = 30$ independent benchmark iterations preceded by 5 warmup iterations per scenario. Metrics report sample mean, sample standard deviation ($\pm \sigma$), and median in milliseconds.
- **Memory Profiling**: Deterministic heap profiling via standard Python `tracemalloc`.

### 1.3 Evaluated Scenarios
1. **Photographic Image (Fine Grid)**: `docs/images/t4.png` ($612 \times 408$ pixels, RGB, 24-bit), partitioned into an $M \times N = 18 \times 12$ grid (216 tiles of size $34 \times 34$ pixels).
2. **Synthetic Standard Pattern (Square Grid)**: Standard benchmark pattern ($768 \times 512$ pixels, RGB, 24-bit), partitioned into an $M \times N = 16 \times 16$ grid (256 tiles of size $48 \times 32$ pixels).
3. **Synthetic Standard Pattern (Non-Square Grid)**: Standard benchmark pattern ($768 \times 512$ pixels, RGB, 24-bit), partitioned into an $M \times N = 24 \times 16$ grid (384 tiles of size $32 \times 32$ pixels).

## 5. Key Conclusions from Experimental Evaluation

1. **Lightweight Server Processing**:
   The server-side production engine (`grt_server.py`) completes tile scrambling in **$1.34 - 2.21\text{ ms}$** across standard resolutions ($612 \times 408$ and $768 \times 512$), eliminating server-side bottlenecks without heavy dependencies or complex vectorization.

2. **Client-Side HTML5 Canvas Execution is Extremely Fast**:
   Production JavaScript decryption (`igrt_client.js`) achieves **$0.32 - 0.51\text{ ms}$** descrambling latencies across all evaluated tile grids, well within the standard $16.6\text{ ms}$ budget required for smooth 60 FPS viewport rendering.

3. **The Compression Dilemma Dictates Tile-Level Architecture**:
   Conversely, tile-level GRT transposition preserves intra-tile spatial autocorrelation, restricting bandwidth growth to **$+7.4\%$ to $+8.0\%$** on PNG and **$+9.3\%$ to $+19.3\%$** on WebP.

4. **Zero-Fixed-Point Security Guarantees**:
   By introducing translation offsets $(r_m, r_n)$, GRT displaces the origin tile $(0,0) \to (r_m, r_n)$, closing the fixed-point vulnerability that affects Arnold Cat Map, and preventing automated crawlers from using the top-left tile as an anchor point.
