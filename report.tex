\section{Introduction}

\subsection{Problem Statement}
Images are an essential part of many online platforms, such as online comic readers, webtoon sites, photography portfolios, and e-commerce stores. These images are typically delivered through Content Delivery Networks (CDNs) so that users around the world can load them quickly. However, this open delivery model also makes images easy targets for automated scraping. Anyone with basic command-line tools like \texttt{curl} or simple Python scripts can download thousands of images in minutes at almost no cost. In addition, unauthorized websites often practice ``hotlinking'' by embedding image URLs directly into their own pages, consuming the original server's bandwidth without giving it any traffic.

Standard security approaches do not solve this problem well:
\begin{itemize}
    \item \textbf{HTTPS / TLS:} HTTPS only protects data while it is traveling over the network. Once the image reaches the user's browser, it is stored in clear form in memory or browser cache, where any scraping script can easily copy it.
    \item \textbf{The Display Problem (Analog Hole):} Because images must eventually be shown on screen to human users, we cannot keep them encrypted in the final display. If we use standard decryption (like AES) on the full image file, scrapers can simply intercept the decrypted file right before rendering.
    \item \textbf{Pixel-Level Scrambling and File Size:} Traditional image encryption techniques (such as Arnold's Cat Map) scramble individual pixels. While this hides the image, it completely ruins the smooth color transitions between neighboring pixels. Standard web formats like PNG, WebP, and JPEG rely on these smooth transitions to compress data. When pixels are shuffled randomly, the image turns into noisy data, and file sizes increase by $300\%$ to $600\%$. This causes high bandwidth bills and slow page loading.
\end{itemize}

To address these issues, we look at tile-level image scrambling using the Generalized Rectangular Transform (GRT). Instead of shuffling individual pixels, we divide the image into a grid of small rectangular tiles and shuffle the tiles. Because each tile keeps its original internal pixels intact, compression algorithms still work effectively, while unauthorized downloaders only see an unreadable jigsaw puzzle.

\subsection{Objectives}
In this project, our goals are:
\begin{itemize}
    \item Implement the Generalized Rectangular Transform (GRT) in Python on the server to scramble images into tiles, and implement the Inverse GRT (IGRT) in JavaScript to reconstruct the original image on an HTML5 Canvas in the browser.
    \item Fix the stationary origin flaw found in simpler transforms (where the top-left tile at position $(0,0)$ never moves) by adding a translation offset vector $(r_m, r_n)$.
    \item Verify that the scrambling is 100\% reversible, meaning the reconstructed image matches the original image pixel-by-pixel with zero quality loss ($\text{MSE} = 0.0$, $\text{PSNR} = \infty$).
    \item Measure execution speed, memory usage, and file size across PNG, WebP, and JPEG to see if this approach is fast and lightweight enough for practical web delivery.
\end{itemize}

\section{Theoretical Background and Mathematical Formulations}
% [Assigned to Nguyen Tung Duong, Tran Mai Anh]

\subsection{Notations and Terminology}
We divide an image of width $W$ and height $H$ into a grid of $M \times N$ rectangular tiles, where $M$ is the number of tile columns and $N$ is the number of tile rows. Each tile has width $T_w = W / M$ and height $T_h = H / N$.

We represent the position of each tile using coordinates $(x, y)$, where $x \in \{0, 1, \dots, M-1\}$ and $y \in \{0, 1, \dots, N-1\}$. When the image is scrambled, tile $(x, y)$ moves to a new position $(x', y')$.

We define the shared grid factor $p$ as:
\begin{equation}
    p = \gcd(M, N)
\end{equation}
The reduced aspect ratio factors are:
\begin{equation}
    h = \frac{M}{p}, \quad v = \frac{N}{p}, \quad \text{with } \gcd(h, v) = 1
\end{equation}

\subsection{From Arnold Cat Map to Special Rectangular Transform (SRT)}
The well-known Arnold Cat Map only works on square images where $M = N$, and decrypting it requires repeating the forward transform many times until the image happens to return to its initial state. 

To handle rectangular images with direct decryption, Lan and Wang (2025) proposed the Special Rectangular Transform (SRT):
\begin{equation}
    \begin{bmatrix} x_{n+1} \\ y_{n+1} \end{bmatrix} = \begin{bmatrix} 1 & r \\ s & rs + 1 \end{bmatrix} \begin{bmatrix} x_n \\ y_n \end{bmatrix} \bmod \begin{bmatrix} M \\ N \end{bmatrix}
\end{equation}
By choosing parameters such that $(r \bmod h = 0 \lor s \bmod v = 0)$ and $\gcd(rs + 1, v) = 1$, the equations decouple, allowing direct inversion in two steps. 

However, SRT has a notable weakness: because it is a linear transform with no shift, the tile at $(0, 0)$ always stays at $(0, 0)$:
\begin{equation}
    \begin{bmatrix} 1 & r \\ s & rs + 1 \end{bmatrix} \begin{bmatrix} 0 \\ 0 \end{bmatrix} \equiv \begin{bmatrix} 0 \\ 0 \end{bmatrix} \pmod{\begin{bmatrix} M \\ N \end{bmatrix}}
\end{equation}
This means the top-left tile never moves, giving scrapers a fixed reference point to start piecing the image back together.

\subsection{Generalized Rectangular Transform (GRT)}
To ensure every tile moves, the Generalized Rectangular Transform (GRT) adds an offset vector $\begin{bmatrix} r_m \\ r_n \end{bmatrix}$:
\begin{equation}
    \begin{bmatrix} x' \\ y' \end{bmatrix} = \left( \begin{bmatrix} a & b \\ c & d \end{bmatrix} \begin{bmatrix} x \\ y \end{bmatrix} + \begin{bmatrix} r_m \\ r_n \end{bmatrix} \right) \bmod \begin{bmatrix} M \\ N \end{bmatrix}
\end{equation}
Now, the origin tile $(0, 0)$ moves to $(r_m, r_n)$, removing the stationary corner problem.

\subsection{The 4 Reversibility Conditions}
For the transform to be one-to-one (every tile maps to a unique position and can be recovered), the matrix parameters $a, b, c, d$ must satisfy four conditions:
\begin{enumerate}
    \item \textbf{Condition 1:} $(b \bmod h = 0) \lor (c \bmod v = 0)$. This prevents horizontal and vertical wrap-around terms from mixing during decryption.
    \item \textbf{Condition 2:} $\gcd(|G|, p) = 1$, where $|G| = |ad - bc|$. This ensures that the matrix can be inverted modulo $p$.
    \item \textbf{Condition 3:} $\gcd(a, h) = 1$. This ensures unique mapping along the horizontal quotient factor $h$.
    \item \textbf{Condition 4:} $\gcd(d, v) = 1$. This ensures unique mapping along the vertical quotient factor $v$.
\end{enumerate}

\subsection{The 4-Stage Exact Inversion (IGRT)}
When these four conditions hold, we can recover original tile coordinates $(x, y)$ from scrambled coordinates $(x', y')$ in four steps:
\begin{itemize}
    \item \textbf{Stage 1 (Equilateral Inverse):} First, subtract $(r_m, r_n)$ and invert modulo $p$ to find the remainders $(x_p, y_p)$:
    \begin{equation}
        \begin{bmatrix} x_p \\ y_p \end{bmatrix} = |G|_{[p]}^{-1} \begin{bmatrix} d & -b \\ -c & a \end{bmatrix} \begin{bmatrix} x' - r_m \\ y' - r_n \end{bmatrix} \bmod p
    \end{equation}
    \item \textbf{Stage 2 (Projection Mapping):} Compute the projected quotient differences $(H, V)$:
    \begin{equation}
        \begin{bmatrix} H \\ V \end{bmatrix} = \left( \left\lfloor \frac{\begin{bmatrix} x' - r_m \\ y' - r_n \end{bmatrix} - \begin{bmatrix} a & b \\ c & d \end{bmatrix} \begin{bmatrix} x_p \\ y_p \end{bmatrix}}{p} \right\rfloor \right) \bmod \begin{bmatrix} h \\ v \end{bmatrix}
    \end{equation}
    \item \textbf{Stage 3 (Triangular Uncoupling):} Solve for $(x_h, y_v)$ using modular inverses of $a$ and $d$. Depending on whether $b \bmod h = 0$ or $c \bmod v = 0$, this reduces to a simple triangular system.
    \item \textbf{Stage 4 (Assembly):} Combine the remainders and quotients to obtain the original coordinates:
    \begin{equation}
        x = x_p + p \cdot x_h, \quad y = y_p + p \cdot y_v
    \end{equation}
\end{itemize}

\section{Algorithm Design and System Implementation}
% [Assigned to Nguyen Tung Duong, Ta Quang Huy]

\subsection{System Architecture and Workflow}
The workflow of our anti-scraping system is straightforward and fits easily into standard web architectures:
\begin{enumerate}
    \item \textbf{Server Scrambling:} When an image is uploaded or published, the Python backend splits it into $M \times N$ tiles, shuffles them using the forward GRT formula, and saves the scrambled image as a normal WebP or PNG file.
    \item \textbf{CDN Storage:} The scrambled image is stored on a public CDN. Any automated tool that downloads the image directly (like \texttt{curl} or a scraper) only gets a scrambled mosaic.
    \item \textbf{Client Delivery:} When an authorized user visits the webpage, the browser downloads the scrambled image and receives the transform parameters $(a, b, c, d, r_m, r_n)$ for that session.
    \item \textbf{Canvas Assembly:} A small JavaScript script on the webpage uses IGRT to put the tiles back into their correct positions and draws the clean image onto an HTML5 Canvas element.
\end{enumerate}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.92\textwidth]{docs/images/visualize.png}
    \caption{Overview of the anti-scraping pipeline: Python server scrambles tiles, CDN serves scrambled images, and client JavaScript unscrambles onto an HTML5 Canvas.}
    \label{fig:pipeline}
\end{figure}

\subsection{Server Implementation in Python (\texttt{grt\_server.py})}
The server script is written in Python 3.10 and only uses NumPy and Pillow (PIL):
\begin{itemize}
    \item \textbf{Parameter Checking:} The function \texttt{validate\_grt\_parameters} verifies that the chosen parameters satisfy Conditions 1 through 4 before scrambling begins.
    \item \textbf{Tile Slicing:} Using NumPy 2-D array slicing, tiles are extracted and copied into their new positions quickly without extra intermediate buffers.
    \item \textbf{Edge Padding:} If the image width or height is not cleanly divisible by $M$ or $N$, \texttt{pad\_image\_to\_grid} adds a few border pixels so the tiles divide evenly.
\end{itemize}

\subsection{Client Implementation in JavaScript (\texttt{igrt\_client.js})}
The client script runs in the browser using vanilla JavaScript without any external libraries:
\begin{itemize}
    \item \textbf{Safe Modulo Function:} JavaScript's \texttt{\%} operator can return negative values for negative numbers, which leads to wrong array indices. We use \texttt{mod(n, m) = ((n \% m) + m) \% m} to always keep results positive.
    \item \textbf{Precomputed Tables (LUTs):} All modular inverse and division operations are calculated once before the tile loop and stored in 1-D TypedArrays. Inside the loop, finding the original position of a tile is just a quick table lookup.
    \item \textbf{Fast Canvas Copying:} We use a \texttt{Uint32Array} view over the canvas image buffer. This allows copying full 32-bit RGBA pixels in single operations, keeping the descrambling fast.
\end{itemize}

\begin{enumerate}
    \item How fast is the scrambling on the server, and can the client decode the image fast enough for a smooth user experience?
    \item How much memory does the server need, and are there any memory leaks?
    \item How much does tile scrambling increase the file size compared to normal images and pixel-level scrambling?

\subsection{Testing Setup}
All tests were conducted on a Windows 11 machine with a modern x86\_64 multi-core processor:
\begin{itemize}
    \item \textbf{Server Environment:} Python 3.10.0 (64-bit), Pillow 10.0, NumPy 1.26.
    \item \textbf{Client Environment:} Node.js v22.19.0 (running Google V8 engine v12.9) for automated measurement, along with a Chromium browser for visual verification on HTML5 Canvas.
    \item \textbf{Timing Method:} For each test, we performed 5 warmup runs followed by $K = 30$ recorded runs. We report the average (mean), standard deviation ($\pm \sigma$), and median time in milliseconds.

\paragraph{Why Tile Scrambling Keeps File Sizes Small:}
\begin{itemize}
    \item \textbf{Pixel Scrambling Breaks Compression:} Image compressors look for patterns, such as neighboring pixels with similar colors. When individual pixels are shuffled, all color patterns disappear and the image looks like random static noise. The compressor cannot find any repeated patterns, which causes a $168.5\text{ KB}$ PNG image to swell to $735.7\text{ KB}$ ($+336\%$).
    \item \textbf{Tile Scrambling Keeps Local Patterns:} In our method, each tile (for example, $34 \times 34$ pixels) remains completely intact inside. The pixels inside the tile still have their original colors and smooth transitions. Artificial sharp edges only appear where tiles touch each other. Because of this, the PNG file size only increases by around $7\%$ to $8\%$, and WebP increases by only $9\%$ to $19\%$.
    \item \textbf{JPEG Compatibility:} JPEG compresses images using $8 \times 8$ pixel blocks. In Scenarios 2 and 3, our tile sizes ($48 \times 32$ and $32 \times 32$) are exact multiples of 8. Because the tile edges line up with JPEG's internal compression blocks, the scrambled JPEG file only increased by $1.1\%$ to $2.2\%$.
\end{itemize}

\subsection{Image Quality and Reversibility}
To confirm that decryption restores the exact original image without any blurred pixels or color changes, we calculated the Mean Squared Error (MSE) and Peak Signal-to-Noise Ratio (PSNR):
\begin{equation}
    \text{MSE} = \frac{1}{W \cdot H \cdot C} \sum_{x=0}^{W-1} \sum_{y=0}^{H-1} \sum_{c=0}^{C-1} \left| P_{\text{original}}(x, y, c) - P_{\text{recovered}}(x, y, c) \right|^2 = 0.0
\end{equation}
\begin{equation}
    \text{PSNR} = 10 \cdot \log_{10} \left( \frac{255^2}{\text{MSE}} \right) = \infty\text{ dB}
\end{equation}
For all tested images, the difference between the original and recovered pixels was strictly zero.

    \item $41$ stress tests with unusual image shapes (e.g., $1 \times 100$ strips, prime-dimension grids like $97 \times 89$, and matrices with negative determinants).
    \item $18$ cross-language tests ensuring that Python scrambling and JavaScript descrambling match byte-for-byte.
    \item A 4-panel visual test page that shows the original, scrambled, decrypted, and pixel-difference canvas side by side.
\end{itemize}
All $148$ tests pass with 100\% success.

\subsection{How this Protects against Web Scraping}
Our approach does not try to be an unbreakable military-grade cipher. Instead, its purpose is to make scraping inconvenient and expensive for attackers while keeping costs very low for legitimate users:
\begin{enumerate}
    \item \textbf{Stops Simple Scrapers (\texttt{curl}, \texttt{requests}):} Scrapers that simply download files from URLs will only get scrambled image files. They cannot use these images directly because the contents are shuffled.
    \item \textbf{Stops Direct Hotlinking:} Third-party pirate sites cannot hotlink our image URLs into regular \texttt{<img>} tags. Without our custom JavaScript code running on their page, the image will display as a scrambled mosaic on their website.
    \item \textbf{Forces Bots to Use Heavy Browsers:} To get clean images, an attacker must run a full headless browser (such as Puppeteer or Playwright) to execute the JavaScript code on every page. Running a headless browser takes significantly more CPU and RAM than sending a simple HTTP request, making large-scale scraping of thousands of pages much slower and more expensive.
    \item \textbf{Large Jigsaw Puzzle Search Space:} With $216$ tiles (in an $18 \times 12$ grid), the number of possible arrangements is $216! \approx 10^{411}$. Even specialized puzzle-solving algorithms struggle when images contain large areas of flat colors (such as skies, white backgrounds, or simple manga panels).
    \item \textbf{No Stationary Anchor Tile:} In simpler transforms like SRT, the top-left tile at $(0, 0)$ never moves, which could give an attacker a starting point to solve the puzzle. In our GRT implementation, the offset $(r_m, r_n)$ moves the top-left tile to a different location, leaving no fixed tiles.
\end{enumerate}

\section{Conclusion, Limitations, and Future Work}
% [Assigned to Ha Dang Huy, Nguyen Minh Duc]

\subsection{Summary}
In this project, we built and tested an anti-scraping image protection system based on the Generalized Rectangular Transform (GRT):
\begin{itemize}
    \item We implemented a Python scrambling script for the server and a vanilla JavaScript decoding script for HTML5 Canvas in the browser.
    \item By using translation offsets $(r_m, r_n)$, we fixed the stationary origin problem where the top-left tile never moved in earlier transforms.
    \item Client decoding is very fast, taking only $0.32\text{ ms}$ to $0.51\text{ ms}$, which fits comfortably within a standard 60 FPS frame time ($16.6\text{ ms}$) without slowing down the webpage.
    \item Unlike pixel scrambling methods that inflate file sizes by $300\%$ to $600\%$, tile scrambling keeps the file size increase to only $7\%$ to $8\%$ on PNG and $9\%$ to $19\%$ on WebP, while still allowing exact, lossless reconstruction ($\text{MSE} = 0.0, \text{PSNR} = \infty$).
\end{itemize}

\subsection{Limitations}
We also identified several practical limitations:
\begin{itemize}
    \item \textbf{Screenshots (The Analog Hole):} Once an image is displayed cleanly on the user's screen, nothing can stop a user from taking a manual screenshot (using PrintScreen or snipping tools). This defense is meant to stop automated bulk downloading, not individual manual screenshots.
    \item \textbf{Grid Divisibility:} The image dimensions must be divisible by the grid dimensions $M$ and $N$. If they are not, extra border pixels must be padded before scrambling.
    \item \textbf{Key Delivery:} If the transform keys $(a, b, c, d, r_m, r_n)$ are sent in clear text in public API responses without authentication, an attacker could write a script to read the keys and decrypt the files automatically.
\end{itemize}

\subsection{Future Work}
In future improvements, we plan to:
\begin{itemize}
    \item \textbf{Session-Bound Keys:} Connect transform keys to user session tokens or one-time tokens so keys cannot be easily reused by bots.
    \item \textbf{WebGL / WebGPU Acceleration:} Write a WebGL or WebGPU shader for decoding, which could make it possible to decode very high-resolution images (like 4K photos) or video tiles even faster.
    \item \textbf{Invisible Watermarking:} Add a faint, imperceptible digital watermark with the user's ID into the tiles before scrambling, so that if someone takes a screenshot and reposts it, the source can still be identified.
\end{itemize}
